# Architecture Review 1

**Milestone checkpoint, Plan §5** — written after TPMT (Phase 2), DPYD (Phase 3), and SLCO1B1 (Phase 4) were all implemented end to end, per the plan's own instruction to pause feature development here rather than carry momentum straight into CYP2C19. Same checkpoint discipline as the ACMG classifier project's BRCA1 generalization test.

This is not a status recap — Phases 2-4's `HANDOFF.md` entries already cover what was built. This document answers the plan's six questions concretely, with reference to the actual code as it exists today, not as it was originally envisioned in Phase 1.

## 1. Which concepts turned out to be genuinely universal?

Genuinely universal, unmodified since Phase 1, exercised identically by all three genes:

- **The Layer 1-4 separation itself** (`ObservedVariant` → `AlleleCall`/`Diplotype` → `PhenotypeAssignment` → `RecommendationResult`, aggregated in `PGxResult`). No gene needed a field added to any of these dataclasses to represent its calling logic. `activity_score` (added in Phase 1 speculatively, ahead of DPYD's arrival) turned out to be exactly the right shape when DPYD actually needed it in Phase 3 — nullable-by-default was the correct call.
- **The two-tier evidence provenance split** (`AlleleDefinitionProvenance` / `PhenotypeEvidenceProvenance`, kept structurally separate from a single undifferentiated evidence field). All three gene modules populate both independently, with genuinely different version strings (TPMT: dbSNP 2026-08-16 / CPIC 2018; DPYD: dbSNP 2026-08-16 / CPIC 2017; SLCO1B1: dbSNP 2026-08-16 / CPIC 2022) — the split was necessary in practice, not just in principle.
- **`Confidence`'s non-"supported" states as a genuine, load-bearing vocabulary.** `AMBIGUOUS`, `INSUFFICIENT_DATA`, and `UNSUPPORTED_ALLELE` are each exercised by real fixture-backed tests in all three gene modules. This is the one piece of Phase 1 design that most clearly paid for itself: "never silently guess" (Plan §8) turned into the same three-way branch in every gene module's top-level function.
- **The zygosity vocabulary itself** — `hom_ref` / `het` / `hom_alt` / `missing` / `absent` / `unsupported`, distinguishing "confirmed reference," "explicit no-call," "no record at all," and "a real but different variant at this position." Every gene module needs exactly these six states and no others. This is a genuinely universal *concept*. Whether it's universal *code* is a different question — see §5.
- **The "models → genes is one-way" local-import pattern** (`from pgx_interpreter.models import PGxResult` inside each `call_*` function, to avoid a circular import while keeping `models.py` gene-agnostic). Present identically in all three modules.

## 2. Which concepts are gene-specific, and does the architecture let them stay that way?

Yes — this is the more important half of RQ2, and the answer is genuinely yes, not "yes with caveats forced in by the schema":

- **Phenotype terminology is free text, not a constrained enum or lookup table.** `PhenotypeAssignment.phenotype: str` was a Phase 1 decision that turned out to matter a lot: TPMT/DPYD use "Normal/Intermediate/Poor Metabolizer," SLCO1B1 uses "Normal/Decreased/Poor function." Nothing in the schema needed to change for SLCO1B1 to use different words for a different biological concept (drug transport vs. drug metabolism). If `phenotype` had been a Phase 1 enum of metabolizer categories, SLCO1B1 would have forced a schema change in Phase 4 to accommodate a phenotype-assignment model the plan explicitly wanted to be different (Plan §2: "SLCO1B1 is a drug transporter rather than a metabolizing enzyme").
- **`activity_score` is populated by exactly one gene (DPYD) and stays `None` for the other two.** This is the field doing its intended job: present in the schema from Phase 1, meaningless for two-thirds of the genes that use the schema, and that's fine — nullability was the right design, not a compromise.
- **DPYD's four-independent-locus control flow is genuinely different in shape from TPMT/SLCO1B1's two-linked-variant model**, not just different in the numbers. TPMT and SLCO1B1 each resolve a single haplotype block via one dosage-truth-table function. DPYD calls four independent loci (three simple, one — HapB3 — with its own internal two-variant sub-logic) and only then decides whether more than one is simultaneously non-reference. Forcing DPYD into TPMT's `_call_3_family_diplotype` shape would have meant pretending DPYD's four loci sit on one haplotype block, which they don't — a real biological difference, not an implementation convenience. The architecture accommodates this by simply not sharing that function between DPYD and the other two; each gene module owns its own top-level control flow.
- **`alternative_diplotypes` is populated by TPMT and SLCO1B1 (both hit real unphased-ambiguity cases) but never by DPYD.** Checked directly against the code: `grep alternative_diplotypes pgx_interpreter/genes/*.py` shows it referenced in `tpmt.py` and `slco1b1.py`, absent from `dpyd.py` entirely. DPYD's multi-locus-non-reference case reports `unsupported_allele` outright rather than enumerating phase candidates across unlinked loci — a deliberate scope-narrowing decision (see `dpyd.py`'s module docstring), not an oversight, and the schema doesn't force DPYD to populate a field its model doesn't produce.

## 3. What assumptions had to be removed or generalized along the way?

- **The project plan's own description of SLCO1B1 as "largely single-variant-driven" was wrong**, and had to be corrected during Phase 4 research, not carried into the implementation. CPIC's actual 2022 guideline assigns clinical function to 13 star alleles across a real diplotype system; the single-variant framing belongs to the DPWG guideline, which CPIC's own summary literature explicitly contrasts with its approach. Corrected directly in `slco1b1.py`'s module docstring rather than quietly building to the plan's original framing.
- **DPYD's D949V (c.2846A>T) was initially assumed to be a no-function variant** during Phase 3 research; CPIC's own table classifies it as decreased function (score 0.5). Caught before any code was written, via direct primary-source extraction rather than reliance on memory.
- **`alternative_diplotypes` did not exist in Phase 1's schema at all.** It was added in Phase 2, once TPMT's `*3A` vs `*3B`/`*3C` case made it clear a single `Diplotype` field couldn't represent a genuine two-candidate ambiguity. This is the one real schema generalization event across all four phases — and it was additive (one new field with a default), not a breaking change: Phase 1's 9 tests needed a single-line update (an empty-list addition to a hand-derived expected dict) and passed unchanged otherwise.
- **The assumption that "two variants on one haplotype block" is a TPMT-specific concept had to be revised.** It turned out to be a general shape that recurred exactly once more (SLCO1B1) and did not recur a third time (DPYD's HapB3 pair is two variants but explicitly *not* always in complete LD, which is a different problem — see §5). One recurrence plus one genuine non-recurrence is a real, if small, data point on whether this shape deserves its own shared abstraction — see §6.

## 4. Did any Phase 1 schema field turn out badly designed, unused, or insufficient?

Checked directly against the code rather than by memory:

- **`Confidence.UNRESOLVED` is defined and has never been produced by any of the three real gene modules.** `grep -rn UNRESOLVED pgx_interpreter/` finds it only in `models.py`'s enum definition; the only place it's referenced at all is a structural test (`test_confidence_enum_covers_all_scientific_guardrail_states`) that checks the enum's value set exists, not that anything produces it. It's plausible a future gene (CYP2C19, or a rarer allele combination) will need a genuinely distinct "unresolved" state from `ambiguous`/`insufficient_data`/`unsupported_allele`, but three real gene implementations in, nothing has needed it yet. Worth watching, not worth removing pre-emptively — but flagged here as unused, not silently ignored.
- **`ObservedVariant.genotype_quality` has never been populated by any real code path.** `normalize.py`'s `parse_vcf()` does not parse a GQ field from VCF FORMAT columns, and no gene module reads it. This is a genuine Phase 1 speculative field that hasn't been needed yet — real VCFs carry GQ routinely, so this isn't wrong to have, but it's evidence the field was added ahead of an actual consumer, unlike `activity_score`, which was added ahead of a consumer that materialized in Phase 3 exactly as anticipated.
- **`schema.validate()` is never called by any gene module's real pipeline.** `grep -rln "validate("` across `pgx_interpreter/` and `tests/` shows it defined in `schema.py` and exercised only in `tests/test_models.py` against a hand-built example — no `call_tpmt`/`call_dpyd`/`call_slco1b1` output has ever actually been run through schema validation outside that one Phase 1 test. This is a real gap: the whole point of a JSON Schema was to catch a malformed `PGxResult.to_dict()` output, and right now nothing in the real pipeline exercises that check end to end. Worth wiring in — either as a debug-mode assertion in each gene module's return path, or (more likely the right layer) once the Phase 6 report layer exists and has one place all gene outputs pass through.
- **Everything else from Phase 1 — `PhaseStatus`, the two-tier provenance dataclasses, `rsid`, `zygosity`'s three-way "het"/"hom_alt"/"hom_ref"/`None` shape — has been exercised by all three genes with zero modification.** The schema held up well; the three findings above are narrow and specific, not signs of a shaky foundation.

## 5. Did any gene require special-case logic?

Yes, in two genuinely different ways:

- **DPYD's HapB3 handling** (`_call_hapb3_zygosity` in `dpyd.py`) is special-cased relative to DPYD's own other three loci: it's the only one of the four loci with its own internal two-variant sub-logic (intronic-preferred, exonic-fallback, disagreement-reporting), reproduced directly from PharmCAT's documented behavior rather than derived from this project's general zygosity model.
- **TPMT's *2-locus-must-be-clean-for-*1/*1 rule**, and its mirror in SLCO1B1's four-allele model not needing an equivalent rule because SLCO1B1 (as scoped here) only has one haplotype block to check, not TPMT's haplotype-block-plus-independent-third-locus structure. This isn't so much "special-case logic added" as "a rule TPMT needed that SLCO1B1's narrower scope never triggers" — worth noting as a scope artifact, not a genuine architectural difference: if SLCO1B1's `*14`/`*20` increased-function alleles were ever added, that gene would likely need the same kind of "is every relevant locus confirmed clean before claiming *1/*1" rule TPMT has.
- **The "report the first blocking issue found, rather than exhaustively cross-checking every locus's coverage status in one result" convention appears independently in both `tpmt.py` and `dpyd.py`'s module docstrings**, arrived at separately rather than through any shared code enforcing it. It is not violated anywhere, but it is also not *guaranteed* anywhere — a future gene module could silently do something different and nothing in the architecture would catch it.

## 6. Is that special-case logic biologically justified, or technical debt?

**HapB3's special-casing is biologically justified, not technical debt.** The intronic-preferred/exonic-fallback logic exists because the two HapB3-defining variants are not in complete linkage disequilibrium in real populations (a genuine, cited population-genetics finding, not an implementation convenience) — a generic "treat two variants on a haplotype block the same way TPMT does" rule would have produced real false positives here (documented directly in `dpyd.py`'s docstring and exercised by `test_hapb3_exonic_tag_without_causal_intronic_variant_is_not_called`). This is exactly the kind of gene-specific logic Plan §2 anticipated needing, and the architecture correctly keeps it contained to DPYD's module rather than leaking into the shared model.

**The TPMT/SLCO1B1 structural duplication is technical debt, though a small and currently-affordable amount.** `_zygosity_at`, `_find_variant`, and `_undetermined_diplotype` are reimplemented near-verbatim in all three gene modules (`grep -c _zygosity_at pgx_interpreter/genes/*.py` shows the helper defined and called multiple times in each file, independently). More specifically, `tpmt.py`'s `_call_3_family_diplotype` and `slco1b1.py`'s `_call_slco1b1_diplotype` are the same nine-branch genotype-dosage truth table with different allele names and phenotype terms substituted in — not a coincidence of similar problems solved similarly, but the literal same function shape, confirmed by reading both side by side during Phase 4.

This was deliberately **not** refactored during Phase 4, for a specific reason worth recording: after only TPMT existed, generalizing its truth table into a shared helper would have been premature abstraction from a single example. Now that there are three real gene implementations — two that share the exact shape (TPMT, SLCO1B1) and one that provably does not (DPYD, whose four-independent-locus model cannot be expressed as "two variants on one haplotype block" no matter how the shared helper were designed) — there is enough evidence to make a real decision rather than a guess:

**Recommendation:** extract the zygosity-vocabulary helpers (`_zygosity_at`, `_find_variant`, `_undetermined_diplotype`, the `UNDETERMINED` sentinel) into a shared `pgx_interpreter/genes/_shared.py` (or similar) module — these are genuinely gene-agnostic and have been proven so three times over with zero divergence. **Do not** yet extract the two-linked-variant dosage truth table itself into a shared function — two data points (TPMT, SLCO1B1) is enough to notice the pattern and record it here, but not enough to be confident about the right shared interface, especially since a fourth gene (CYP2C19, next in scope after this review) may reveal a third variation on the theme rather than a third confirmation of this exact one. Revisit this specific question again once CYP2C19 exists.

## Summary

The Phase 1 architecture has held up well across three genes with genuinely different phenotype-assignment models. The places it needed to bend (the additive `alternative_diplotypes` field, the free-text `phenotype` string, the nullable `activity_score`) bent cleanly, without breaking existing tests or forcing a gene's biology into a shape it didn't fit. The places it hasn't bent yet (`UNRESOLVED`, `genotype_quality`, unwired `schema.validate()`) are honestly unused rather than silently broken. The one clear piece of accumulated technical debt — duplicated zygosity-helper code across three gene modules — is real, has a specific low-risk fix identified above, and was left deliberately unaddressed until this checkpoint rather than guessed at after a single example.

CYP2C19 (Phase 8, per the plan's phase numbering) is next, and is a genuine test of this review's conclusions: does the shared-helper extraction recommended above still look right once a fourth, more complex gene (star alleles including known structural-variant considerations, per Plan §9) is in the picture?
