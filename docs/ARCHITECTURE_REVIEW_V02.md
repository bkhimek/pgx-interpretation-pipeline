# Architecture Review 2

**Milestone checkpoint, Plan §5** — written after Phases 5-9 (`evidence.py`'s Tier 2 adapter, `report.py`'s five renderers, CYP2C19, `cli.py`/`main.nf` orchestration) plus three further sessions beyond the plan's original phase numbering: NUDT15 (this project's fifth and narrowest-scope gene), CYP2C19's second Tier 2 drug pairing (voriconazole), and the NUDT15 compound TPMT+NUDT15 recommendation's generalization to all three of CPIC's compound thiopurine tables. Architecture Review 1 (`docs/ARCHITECTURE_REVIEW_V01.md`) covered Phases 2-4 (TPMT, DPYD, SLCO1B1) and closed with one explicit open question for CYP2C19 to answer. This review covers everything since, using the same six questions and the same discipline: claims are checked directly against the code (grep, direct reads), not reconstructed from memory or from what earlier `HANDOFF.md` entries said was intended.

Five gene modules, a Tier 2 evidence layer, a five-format report layer, and a CLI/Nextflow orchestration layer now exist. This is a much larger surface than Architecture Review 1 reviewed, so this document is organized the same way but weighted toward what actually changed or was newly tested, not a re-litigation of Phases 2-4's already-settled conclusions.

## 1. Which concepts turned out to be genuinely universal?

- **Architecture Review 1's own recommendation — extracting `_zygosity_at`, `find_variant`, and `undetermined_diplotype` into `genes/_shared.py` — held up completely.** Checked directly: CYP2C19 (`cyp2c19.py`) and NUDT15 (`nudt15.py`) both import from `genes/_shared.py` exactly like TPMT/DPYD/SLCO1B1 already did, with zero divergence and zero gene-specific override of any of the three functions. That's five gene modules now consuming the same shared zygosity vocabulary, not three — the strongest possible confirmation of AR1 §6's extraction call.
- **`models.py` has had zero schema changes since Phase 6's `interpretation_notes` addition.** This is the standout finding of this review. In the phases since AR1, this project added a fourth and fifth gene, a second Tier 2 drug pairing for an existing gene (CYP2C19 + voriconazole), and a Tier 2 recommendation keyed on *two* genes' phenotypes at once (the compound TPMT+NUDT15 tables) — three genuinely new architectural situations Phase 1's schema was never designed with in mind — and none of them required a new field, a changed field, or a broken existing test. `RecommendationResult` (unchanged since Phase 1) turned out to already be general enough to represent "the same recommendation object, attached to two different `PGxResult`s" without any modification.
- **`report.py`'s lack of a gene-uniqueness assumption is real, not an inference from its docstring.** Checked directly: `grep -n "gene ==\|set(gene\|unique\|dedup" pgx_interpreter/report.py` returns zero matches, and `build_report()` stores `results` as a plain `tuple[PGxResult, ...]` with no gene-keyed dict or deduplication step anywhere in its body. This absence of an assumption — not a feature deliberately built for multi-drug-pairing support, since `report.py` (Phase 6) predates CYP2C19's second drug pairing by two phases — is exactly what let `--cyp2c19-voriconazole` ship as a second, independent "CYP2C19" section with zero changes to `report.py` itself.
- **The `drug: Optional[str] = None` evidence-selection parameter pattern, established for `recommend()` when CYP2C19+voriconazole was added, was reused verbatim (not just similarly) for `recommend_compound_thiopurine()` when the NUDT15 compound tables were generalized to three drugs.** Same default-preserves-old-behavior semantics, same "validate against a known-drugs collection, raise `ValueError` naming the valid options" error handling, same pass-through into `cli.py`. Two real uses of the identical shape is enough to call this a genuinely reusable pattern, not a coincidence.
- **`evidence.py`'s fetch-validate-stamp-cache adapter (`fetch_guideline()`, `GuidelineSnapshot`, `cache_dir`) is unchanged since Phase 5** and has now been reused identically by every guideline added since: CYP2C19+clopidogrel, CYP2C19+voriconazole, and the compound TPMT+NUDT15 tables (which reuse the exact same cached guideline record, `PA166104933`, across all three drugs — the guideline itself is one document with three tables, so this is doubly a case of the caching layer needing no change).

## 2. Which concepts are gene-specific, and does the architecture let them stay that way?

AR1 §6 closed with an explicit open question: does the recommendation to *not* extract TPMT/SLCO1B1's shared two-linked-variant dosage table still look right once a fourth gene exists? CYP2C19 answers this directly, and the answer is yes, for a stronger reason than AR1 could have known in advance:

- **CYP2C19 needed neither TPMT/SLCO1B1's two-linked-variant dosage table nor DPYD's four-independent-loci-decline model — it is a genuine third shape.** Three independent single-SNP loci (`*2`, `*3`, `*17`), where double-heterozygosity across two loci is *resolved directly* rather than declined (unlike DPYD's equivalent situation), backed by real evidence checked directly in `cyp2c19.py`'s own docstring: population-genetics data (Sim et al. 2010, PubMed 20665013, showing `*2` and `*17` co-occur on the same haplotype in only 0.3% of `*17`-carrying chromosomes) and PharmVar nomenclature (no defined cis-compound allele combines `*2`+`*3`, unlike TPMT's `*3A`). If the dosage table had been prematurely extracted after only two examples (TPMT, SLCO1B1), CYP2C19 would have had to either force its genuinely different resolve-don't-decline model into that shape, or bypass the shared abstraction entirely — AR1's restraint was the correct call, now confirmed with real evidence rather than a guess.
- **NUDT15 is a fourth shape, and the simplest one in the project: a single locus, no phasing question of any kind.** `nudt15.py`'s own docstring states this directly — "genotype maps to diplotype directly and unambiguously (0/0 → `*1/*1`, 0/1 → `*1/*3`, 1/1 → `*3/*3`)." No dosage table, no independent-loci combination logic, nothing beyond `_shared.py`'s zygosity vocabulary is needed at all. Worth recording as a data point in the *other* direction from CYP2C19: not every new gene generates new special-case logic — the narrowest-scope gene in this project needed none.
- **The compound TPMT+NUDT15 recommendation tables are gene-*pair*-specific, a category AR1 had no reason to anticipate** because no Tier 2 evidence in Phases 2-4 was keyed on more than one gene's phenotype. The architecture accommodated this without changing `PGxResult`'s single-gene shape at all: `recommend_compound_thiopurine()` computes one `RecommendationResult` from both genes' already-computed phenotypes, then attaches the *identical object* to both genes' separate `PGxResult`s via `dataclasses.replace()`. This is a real, non-obvious extension of the schema's meaning (a `RecommendationResult` can now describe a joint fact about two records, not just a fact about the one it's attached to) that required zero schema changes to express.

## 3. What assumptions had to be removed or generalized along the way?

- **An assumption that was never actually encoded in code, but was implicitly true through Phase 6, was falsified by CYP2C19+voriconazole: "one gene has at most one Tier 2 drug pairing."** This is meaningfully different from every AR1 example, where a wrong assumption required an additive code change to fix. Here, the fix required recognizing that `report.py` had never actually built that assumption into its logic in the first place (§1 above) — the assumption lived only in what every gene module's own code happened to do (call `recommend()` once), not in any check the architecture enforced. Worth recording precisely because it's a different failure/success mode than AR1 catalogued: sometimes the schema already tolerates a scenario nobody explicitly designed for, and the actual work is verifying that tolerance directly rather than assuming a change is needed.
- **The assumption that a `RecommendationResult` attaches to exactly one `PGxResult`** was generalized for the same reason, for the compound TPMT+NUDT15 case — the same object, not just the same values, is shared across two results.
- **CYP2C19's own scope required correcting an assumption mid-research, the same "verify against primary sources, don't carry an initial framing forward" discipline AR1 §3 recorded for SLCO1B1 and DPYD.** The initial framing (whether `*2`/`*17` compound heterozygosity could be resolved directly) required real population-genetics and nomenclature verification before being accepted — not simply assumed to be analogous to CYP2C19's `*2`/`*3` case, which is resolved for a *different* reason (no competing cis allele, vs. `*2`/`*17`'s empirical near-zero cis co-occurrence rate). Two superficially similar cases, verified separately, resolved for different documented reasons — a good example of the "never silently guess" discipline applied to the *design* process itself, not just to the runtime code.

## 4. Did any Phase 1 schema field turn out badly designed, unused, or insufficient?

Revisiting AR1 §4's three flagged items directly, with three more gene modules' worth of new evidence:

- **`Confidence.UNRESOLVED` is still completely unused.** `grep -rn "UNRESOLVED" pgx_interpreter/ tests/` (excluding bytecode caches) finds it only in `models.py`'s own enum definition — CYP2C19 and NUDT15 did not need it either, same as TPMT/DPYD/SLCO1B1 before them. AR1's call to leave it defined and watch rather than remove it still looks right: it would be premature to delete a state that's explicitly part of Plan §8's "never silently guess" vocabulary after only five real gene implementations, none of which happened to need it, especially since a future gene with more exotic ambiguity (or CYP2D6, if the "wrap a specialist tool" path in `docs/CYP2D6_FEASIBILITY.md` §5 is ever pursued, since an external caller's own "no confident call" state might not map cleanly onto `AMBIGUOUS`/`INSUFFICIENT_DATA`/`UNSUPPORTED_ALLELE`) could plausibly be the first real consumer.
- **`ObservedVariant.genotype_quality` is still completely unused.** Same grep, same result as AR1 found it two phases ago — `normalize.py` still does not parse a GQ field, and no gene module reads it. Unchanged status, recorded here rather than silently dropped from tracking.
- **`schema.validate()` is now partially wired in, but AR1's actual recommendation was not carried out.** This is worth flagging plainly rather than softened: AR1 said "worth wiring in... once the Phase 6 report layer exists and has one place all gene outputs pass through." Phase 6 has existed since before this review's predecessor sessions began. Checked directly: `tests/test_evidence.py::test_populated_recommendation_validates_against_schema` now calls `validate()` against a real `recommend()` output (an improvement AR1's own gap analysis motivated, even if not by explicit design), but `grep -rn "validate(" pgx_interpreter/report.py pgx_interpreter/cli.py` returns nothing — the real pipeline (`cli.py report` → `report.build_report()` → renderers) still never validates a `PGxResult.to_dict()` against `schema.py`'s JSON Schema before rendering it. This is the one item in this review that is genuinely overdue, not just open.
- **Everything else — `PhaseStatus`, the two-tier-then-three-tier provenance dataclasses, `rsid`, the zygosity vocabulary itself — has been exercised by all five genes with zero modification,** the same conclusion AR1 reached for three genes, now confirmed for five.

## 5. Did any gene require special-case logic?

- **CYP2C19's `*2`/`*17`-resolved-not-declined reasoning** (§2/§3 above) is real special-case logic, entirely contained within `cyp2c19.py`'s own module and docstring — it does not leak into `_shared.py` or `models.py`. It required (and got) real citations, not an assertion.
- **NUDT15 required none at all** — a useful negative data point recorded directly above in §2, since AR1 only had positive examples (DPYD's HapB3, TPMT's *2-locus-clean rule) to draw on.
- **`evidence.py`'s `_compound_category()` abstraction is a new category of special-case logic AR1 had no vocabulary for: gene-*pair*-specific, not gene-specific.** It factors out the four-row categorical shape (both-Normal / one-Intermediate / either-Poor / both-Intermediate-compound) that CPIC's mercaptopurine, thioguanine, and azathioprine compound tables all share structurally, even though the actual dosing text and classification strengths differ per drug (e.g. thioguanine's "one Intermediate" row is Moderate, not Strong like mercaptopurine's; azathioprine's either-Poor row has no dose-reduction fallback at all, unlike the other two).

## 6. Is that special-case logic biologically justified, or technical debt?

- **CYP2C19's special-case reasoning is biologically justified**, exactly as AR1's HapB3 finding was: population-genetics and nomenclature evidence, not implementation convenience, and it stays contained to the one module it's relevant to.
- **`_compound_category()` is justified, and its *timing* is worth recording as a second real instance of AR1 §6's own abstraction discipline, not just a new example.** It was not extracted speculatively — `evidence.py`'s original compound-recommendation implementation (mercaptopurine only, the NUDT15 session) was a single hardcoded table with no shared-category abstraction at all. The abstraction was only introduced once a second and third real table (thioguanine, azathioprine) confirmed the four-row shape actually recurred rather than being a one-off. This is the identical "wait for two-plus real data points before generalizing" discipline AR1 recommended for the zygosity helpers (three data points before extracting) and, separately, explicitly declined to apply prematurely to the two-linked-variant dosage table (still correctly unextracted after five genes, per §2). The same judgment call, applied consistently a third time, in three different parts of the codebase, is a real sign of a repeatable engineering discipline rather than one lucky call.
- **One real, if minor, new technical-debt-shaped observation: two structurally different CLI extension patterns for "a gene gets a second Tier 2 option" now exist side by side, for a documented reason, but with no shared abstraction between them.** `--cyp2c19-voriconazole` is *additive* (adds a second, independent `PGxResult`/report section) because CYP2C19's two drug pairings each attach to one gene's result. `--thiopurine-drug` is a *selector* (default mercaptopurine, choose one) because the compound recommendation already attaches to two genes' results at once, and stacking multiple drug variants would mean rendering up to six sections for one clinical question. `cli.py`'s own module docstring documents this distinction directly and argues it correctly — this is not an inconsistency, the two cases are genuinely different. But it does mean a third "gene needs another Tier 2 option" case, if one arrives, will need to explicitly re-derive which of the two shapes fits rather than there being one obvious pattern to reach for. Worth naming now, at two data points, rather than only noticing it once a third case forces the question — the same "record it early, decide once there's enough evidence" instinct AR1 modeled for the dosage-table question, applied here to flag rather than to resolve.
- **The unwired `schema.validate()` from §4 is the clearest actual technical debt this review found.** It is small, low-risk, and has an unambiguous fix (call `validate()` once inside `report.build_report()` or `_gene_section()`, the one place — per AR1's own suggestion — every gene's output already passes through before rendering). Recorded here rather than fixed in this session, consistent with this review's own scope: a review is a checkpoint that identifies and records, the same restraint AR1 itself modeled by recording its dosage-table recommendation rather than acting on it immediately.

## Summary

The Phase 1 architecture has now held up across five genes, three genuinely different diplotype-calling shapes, two Tier 2 evidence extension patterns (single-gene multi-drug, and multi-gene compound), and a full report/CLI/Nextflow orchestration layer built on top — all without a single schema change since Phase 6. That is a stronger result than Architecture Review 1 could have shown with three genes and no evidence/report/orchestration layers yet built; the design decisions AR1 flagged as working well (free-text `phenotype`, nullable `activity_score`, the additive `alternative_diplotypes` field) have now been joined by an even more striking one: `RecommendationResult`'s single-gene-shaped schema turned out to already tolerate being shared across two genes' results, with zero modification, for a use case (compound two-gene recommendations) that did not exist when the field was designed.

Two concrete, low-risk items are recorded here rather than fixed, matching AR1's own discipline of recording a recommendation and revisiting it once there's a real reason to act: wiring `schema.validate()` into the real `report.py` pipeline (overdue, not just open — see §4), and being deliberate about which of the two existing CLI-extension shapes (additive vs. selector) a future third Tier-2-option case should follow, rather than defaulting to whichever was used most recently (see §6).

CYP2D6 remains the next genuinely hard architectural question this project has identified (see `docs/CYP2D6_FEASIBILITY.md`), but — per that document's own conclusion — it is not a natural extension of any of the five calling shapes reviewed here; it would need a different Layer 1 entirely (alignment-level input, not VCF-only), which is exactly why it remains explicitly out of scope rather than being treated as "gene six."

## Addendum (2026-08-20)

The `schema.validate()` wiring flagged as genuinely overdue in §4/§6 above was carried out the same day, as a standalone closing task rather than a new phase — see `pgx_interpreter/report.py`'s module docstring ("schema.validate() is now wired in here") and the corresponding `HANDOFF.md` entry. `build_report()` now validates every `PGxResult` exactly once, at the one point every result already passes through regardless of gene or output format, raising `ValueError` with the gene, sample, and specific problems on failure. Two new tests confirm both directions: a real four-gene result set validates cleanly, and a deliberately malformed duck-typed stand-in (not a real gene module, since no real gene module can currently produce invalid output — the check exists to catch future schema/model drift) proves the raise path fires with the expected detail. The CLI-extension-pattern question (additive vs. selector) from §6 remains open, correctly left for whenever a third Tier-2-option case actually arrives rather than resolved speculatively now.
